# janitor-waha

Self-hosted **WAHA (WhatsApp HTTP API)** stack for Janitor. Runs `devlikeapro/waha`
on `127.0.0.1:3000`, exposes REST API to send/receive WhatsApp messages, and stores
sessions in a bind-mounted directory so QR-pairing survives container restarts.

This skill covers the **complete lifecycle** proven during the Aug 2026 deploy on
the workstation: engine selection (NOWEB over GOWS), QR + pairing-code flows,
session management, common API calls, troubleshooting, and programmatic integration.

## When to Use

- You need to send/receive WhatsApp messages programmatically (bots, alerts, notifications)
- You're building a tool/agent that integrates with WhatsApp via HTTP
- The user asks to "connect WhatsApp", "send via WhatsApp", "make a WhatsApp bot",
  or "vincular WhatsApp"

## ⚠️ Compliance Warning (READ FIRST)

WAHA uses an **unofficial WhatsApp Web client**. Per WAHA's own docs:
> *"WhatsApp does not allow bots or unofficial clients on their platform, so this
> shouldn't be considered totally safe."*

**Account bans are possible.** Documented mitigations baked into this deploy:
- **NOWEB engine** (Node, no Chromium, fewer fingerprints than WEBJS — see Critical Pitfall #2)
- **Single session per number** (multi-accounting = higher ban risk)
- **Loopback-only** (no public exposure = less abuse signal)
- **No bulk/spam pattern** — automated messages should be triggered by real user requests
- **Reachout Timelock awareness** — see "Shadow Restrictions" section below

The user is responsible for complying with WhatsApp ToS. **Do not use WAHA for
spam, cold outreach, or mass messaging.**

## Architecture

```
Hermes Agent ──HTTP──> janitor-waha :3000 ──WhatsApp Web protocol──> WhatsApp servers
                                │
                                ├─ /app/.sessions  (auth state, persisted in bind mount)
                                └─ /app/.media     (downloaded media, persisted)
```

**Service details:**
- Image: `devlikeapro/waha:latest` (CORE tier, GPL, free)
- Engine: **NOWEB** (Node.js, no Chromium, ~355MB RAM idle) — default since Aug 2026
- Container name: `janitor-waha`
- Bind mount sessions: `${HERMES_HOME:-$HOME/.janitor}/docker/waha/sessions` → `/app/.sessions`
- Bind mount media: `${HERMES_HOME:-$HOME/.janitor}/docker/waha/media` → `/app/.media`
- Port: `127.0.0.1:3000:3000` (loopback only — no LAN exposure)
- DNS: `1.1.1.1, 8.8.8.8` (fix for `web.whatsapp.com` resolution in restrictive networks)
- Log rotation: 100MB × 10 files (json-file driver)
- Auth: `WAHA_API_KEY` (X-Api-Key header) on all `/api/*` endpoints except public dashboard/swagger
- WAHA version verified: **2026.7.2**

## Deploy (First-time)

```bash
~/.janitor/skills/devops/janitor-waha/scripts/deploy.sh
```

The script:
1. Verifies Docker daemon
2. Creates `~/.janitor/docker/waha/{sessions,media}` dirs on the host
3. Generates `waha.env` with random `WAHA_API_KEY` (32 bytes) + dashboard/swagger
   passwords (24 bytes each) — **preserved on re-runs**
4. Writes `waha-compose.yml` if absent (NOWEB engine, abs paths resolved from
   `$HERMES_HOME`, auth-aware healthcheck)
5. Pulls `devlikeapro/waha:latest`
6. Starts the stack
7. Waits for health check (max 90s)
8. Verifies `GET /health` returns 200 with API key
9. Injects `WAHA_BASE_URL` + `WAHA_API_KEY` + dashboard/swagger passwords into `~/.janitor/.env`
10. Prints summary with credentials

**Idempotent**: re-running on a healthy stack is safe — env preserved, no re-pairing needed.

```bash
docker compose --env-file waha.env -f waha-compose.yml up -d
```

## Connecting a WhatsApp Number

WAHA operates on **sessions** — one session = one WhatsApp number. Two auth flows:

### Flow A: QR code (when you're at the workstation)

```bash
WAHA_API_KEY=$(grep '^WAHA_API_KEY=' ~/.janitor/docker/waha.env | cut -d= -f2)

# 1. Create session (NOWEB engine)
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{"name":"default","config":{"engine":"NOWEB"}}' \
  http://127.0.0.1:3000/api/sessions

# 2. Start session (creates SCAN_QR_CODE state)
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" \
  http://127.0.0.1:3000/api/sessions/default/start

# 3. Get QR as PNG
curl -H "X-Api-Key: $WAHA_API_KEY" \
  http://127.0.0.1:3000/api/default/auth/qr \
  --output /tmp/waha-qr.png

# 4. Open the QR (or send to your phone via Telegram)
xdg-open /tmp/waha-qr.png
```

Then in WhatsApp: ⚙️ → Dispositivos vinculados → Vincular un dispositivo → scan.

### Flow B: Pairing code (when you're away from the workstation, e.g. on phone only)

This is the **proven Aug 2026 flow** that worked end-to-end:

```bash
WAHA_API_KEY=$(grep '^WAHA_API_KEY=' ~/.janitor/docker/waha.env | cut -d= -f2)
PHONE="573001234567"   # international format, NO +, NO spaces, NO dashes

# 1+2. Create + start session (NOWEB)
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{"name":"default","config":{"engine":"NOWEB"}}' \
  http://127.0.0.1:3000/api/sessions

curl -X POST -H "X-Api-Key: $WAHA_API_KEY" \
  http://127.0.0.1:3000/api/sessions/default/start

# Wait for SCAN_QR_CODE state
sleep 3

# 3. Request pairing code
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d "{\"phoneNumber\":\"$PHONE\"}" \
  http://127.0.0.1:3000/api/default/auth/request-code
# Returns: {"code":"XXXX-XXXX"}  — 8 chars, format DDDD-DDDD
```

Then in WhatsApp on phone: ⚙️ → Dispositivos vinculados → **"Vincular con número de teléfono"**
(Android) / **"Use phone number"** (iOS) → enter the 8-char code (with or without dash).

**Code expires in ~60s** (be conservative — could be slightly less if WhatsApp throttles).
If you miss it, just re-call the request-code endpoint — no need
to restart the session.

**After the user types the code, the pairing may silently fail at the protocol
layer even though WAHA returned 200.** Before declaring success or failure,
check the container logs — this is the lesson from the GOWS pairing-code bug
(see Pitfall #2 and the umbrella pattern "API 200 ≠ third-party protocol worked"
in `janitor-docker-selfhost`):

```bash
docker logs janitor-waha --since 30s | grep -iE "error|fail|warn|ephemeral|link_code"
# If you see "missing <link_code_pairing_wrapped_primary_ephemeral_pub>" the engine is broken.
# Switch to NOWEB and re-pair.
```

**Helper script** automates steps 1-3:
```bash
~/.janitor/skills/devops/janitor-waha/scripts/pair-waha.sh 573001234567
# Prints: Pairing code: 75LK-ZLX3  (or QR PNG path)
```

### Verify connection

```bash
WAHA_API_KEY=$(grep '^WAHA_API_KEY=' ~/.janitor/docker/waha.env | cut -d= -f2)

# CORRECT endpoint (WAHA docs typo uses /api/{session}/me without "sessions")
curl -H "X-Api-Key: $WAHA_API_KEY" http://127.0.0.1:3000/api/sessions/default/me

# Returns:
# {
#   "id": "573001234567@c.us",
#   "pushName": "Example User",
#   "lid": "147205776220320@lid",
#   "jid": "573001234567:95@s.whatsapp.net",
#   "reachoutTimelock": null
# }
```

If `status` is `WORKING` and `me.id` matches your phone — pairing succeeded.

## Session State Machine

| Status | Meaning | Next action |
|--------|---------|-------------|
| `STOPPED` | Session created but not started | Call `POST /api/sessions/{name}/start` |
| `STARTING` | Engine booting | Wait 5-15s |
| `SCAN_QR_CODE` | Awaiting auth (QR or pairing code) | Scan QR or call `request-code` |
| `PASSKEY_REQUIRED` | WhatsApp asking for WebAuthn passkey | See Passkey section below |
| `PASSKEY_CONFIRMATION_REQUIRED` | User must confirm a code | Check event payload `data.code` |
| `WORKING` | Connected and ready | Send messages |
| `FAILED` | Auth lost or network issue | `restart` → if no help, `logout` + `start` |

### Phone number format

`PHONE@c.us` where `PHONE` is the international number **without** `+`, spaces, or dashes.

| Country | Local format | WAHA format |
|---------|--------------|-------------|
| Colombia | `+57 300 1234567` | `573001234567@c.us` |
| México | `+52 55 1234 5678` | `525512345678@c.us` |
| España | `+34 612 345 678` | `34612345678@c.us` |

**For groups:** use `GROUPID@g.us` (group ID has ~18 digits + timestamp suffix, get from

## Shadow Restrictions (Reachout Timelock)

WhatsApp silently **shadow-restricts** accounts that message too many **new contacts**
(cold outreach). The session stays `WORKING` and connected — but messages to new
contacts fail with HTTP error `463` until the lock lifts.

**Symptoms:**
- `GET /api/sessions/{name}/me` shows `reachoutTimelock.isActive: true`
- Webhook `session.status WORKING` event carries `data.reachoutTimelock`
- Send messages to existing chats work; new chats fail

**DO NOT:**
- Restart the session
- Logout and re-pair
- These do NOT lift the restriction

**DO:**
- Pause outreach to new contacts
- Wait until `reachoutTimelock.timeEnforcementEnds` (unix timestamp, seconds)
- WAHA re-emits `WORKING` event with `isActive: false` when it lifts
- Messaging existing chats continues to work during the lock

## Critical Pitfalls (Learned Aug 2026)

### 1. `/health` requires API key when `WAHA_API_KEY` is set

The official compose ships with `WAHA_API_KEY=*** — insecure placeholder`. Any real
API key activates auth on `/health` too. The healthcheck in `waha-compose.yml` passes
the key via `$WAHA_API_KEY` (read from `env_file`). **Do NOT simplify to
`wget http://.../health` — it 401s and healthcheck fails forever.**

Symptom: container starts, stays in `health: starting` forever, never becomes `healthy`.

### 2. Engine GOWS has a pairing-code bug (Aug 2026, confirmed)

**Symptom:** `POST /api/{session}/auth/request-code` returns an 8-digit code correctly,
but WhatsApp rejects it as "incorrect" even when typed immediately. WAHA logs show:

```
ERROR [Session/default/Client] Failed to handle code pair notification:
missing <link_code_pairing_wrapped_primary_ephemeral_pub> element in notification
{"engine":"gows"}
```

**Cause:** WAHA Core 2026.7.2 + GOWS engine doesn't fully implement the
`link_code_pairing_wrapped_primary_ephemeral_pub` element that WhatsApp sends back
during the code-pairing handshake. WAHA returns the code to the API caller, but when
the user enters it in WhatsApp, the server's response notification can't be parsed
by WAHA and the pairing silently fails.

**Fix:** switch to engine **NOWEB** (Node.js, also no Chromium, ~355MB RAM idle).
Verified working Aug 2026: pairing code returned successfully → status `WORKING` in 40s,
no handshake errors. A self-message test (`573001234567@c.us`) confirmed end-to-end
delivery.

```bash
# In waha.env:
WHATSAPP_DEFAULT_ENGINE=NOWEB

# In session create payload:
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{"name":"default","config":{"engine":"NOWEB"}}' \
  http://127.0.0.1:3000/api/sessions
```

**Fallback engines (ranked by reliability for pairing):**
1. **NOWEB** (recommended) — no Chromium, no GOWS pairing bug, ~355MB
2. **WEBJS** (legacy, heaviest) — Chromium-based, ~600-800MB, most tested but
   most detectable fingerprint. Use only if NOWEB fails for your account type.
3. **WPP** (WhatsApp Web Plus) — third-party patched WEBJS, similar footprint.

### 3. WAHA docs typo: `/me` endpoint location

The WAHA docs and Swagger show `GET /api/{session}/me` — this returns 404.
The **correct** endpoint is `GET /api/sessions/{session}/me` (with `/sessions`).
Always use the longer form.

### 4. Bind mount paths in compose must be absolute

The official compose uses `./sessions:/app/.sessions` — a **relative path**. This
only works if you `cd` into the compose directory before `docker compose up`.
Because our compose lives in `~/.janitor/docker/` and we run from anywhere, we
**always use absolute paths** resolved at deploy time from `$HERMES_HOME` (or
`$HOME/.janitor` as default), written by `deploy.sh` into a generated
`waha-compose.yml`. The bundled template in this skill uses the same convention.

### 5. Sessions directory must exist BEFORE first start

If `/app/.sessions` doesn't exist when the container starts, WAHA creates it as
`root`. Subsequent writes from the unprivileged WAHA user (`node`, uid 1000) fail
with EACCES. **The deploy script creates `sessions/` and `media/` on the host first**
to ensure correct ownership inheritance.

### 6. The `docker_default` network warning is cosmetic

Compose v2 emits `Found orphan containers` because every janitor-* stack joins
the implicit `docker_default` network. **Ignore this warning** — it doesn't
affect runtime. To eliminate, add an explicit `networks: janitor_net: external: true`
block (not done here because all existing stacks share `docker_default`).

### 7. WAHA Plus vs Core — license trap

The official compose hard-codes `devlikeapro/waha-plus` (paid tier). We use
`devlikeapro/waha:latest` (CORE tier, GPL, free). If you see Plus-only endpoints
fail (e.g. certain analytics or multi-account features), that's why. For 95% of
bots/messaging integrations, CORE is sufficient.

### 8. WhatsApp bans: the only real risk

There is no technical mitigation that fully prevents WhatsApp bans for
unofficial clients. The single most important rule: **don't send unsolicited
mass messages**. WAHA is safe for transactional, user-initiated, or
personal-assistant use cases. It is NOT safe for cold outreach or spam.

### 9. NOWEB does NOT download group message history on reconnection

**Symptom:** You enable `noweb.store.enabled=true, fullSync=true`, the session
transitions cleanly to `WORKING`, but `GET /api/default/chats/{groupId}/messages`
returns `200 []` — the in-memory store has no history. Logs show:

```
INFO (NOWEBEngine): Reconnection with existing sync data,
  skipping history sync wait. Transitioning to Online.
```

**Cause:** When NOWEB reconnects to WhatsApp with an existing auth state (and
even with `fullSync=true` set), it transitions to "Online" mode without waiting
for an initial history sync. The store records messages received **after** the
reconnection, not the backlog.

**What works / doesn't:**

| Want | What to do |
|------|------------|
| Read messages **sent after** WAHA came online | Just wait — they appear live |
| Read messages **sent before** WAHA came online | **Impossible in NOWEB** |
| Force a fresh sync | **Requires logout + re-pair** (loses auth, user re-inputs pairing code) |

**Fallback — log + re-pair if you need history:** With fresh auth state and
`fullSync=true`, NOWEB **does** sometimes populate messages on the second
pairing. It does NOT populate contacts (see `references/contacts-and-groups.md`).
Test before relying on it.

**Practical workaround for Aug 2026:** Build tooling that **processes messages
in real-time** (webhook on incoming messages) rather than relying on retroactive
reads. WAHA Plus (paid) gives full history access.

### 10. WAHA Core has no endpoint to delete messages you sent

**Symptom:** You sent a test/spam message to force sync (e.g. "🤖 (sincronizando)")
and want to remove it. Probing `POST /api/deleteMessage`, `DELETE
/api/default/messages/{id}`, etc. all return **404**.

**Reality:** WAHA Core (free tier) does not expose message deletion. The message
remains in the group forever. WAHA Plus adds `deleteMessage`.

**Impact:** Be careful what you send to user-facing groups during debugging. A
test message to a VIP group stays there permanently. If you need to send
diagnostic messages, do it to your own number (`your_own_phone@c.us`) in a
private 1:1 chat — never in a client-facing group.

### 11. Sending a message to "force sync" doesn't populate history (and pollutes the chat)

Even after `noweb.store.enabled=true` and a fresh pairing, sending a message into
a group chat to trigger event delivery **does not retroactively load past
messages**. WAHA receives the new echo message and any messages that arrive
**after** that point — but the backlog stays empty.

If you send a "ping" to a real user group, that's a permanent, visible polluter
in the chat. Always test the sync-into-history behavior in a private 1:1 chat
with yourself first. See Pitfall #10 for the corollary (you can't undo it).

### 12. `/api/sendAudio` does NOT exist — the voice note endpoint is `/api/sendVoice` (Aug 2026)

**Symptom:** Trying to send a voice note bubbles out as `POST /api/sendAudio →
404 Not Found`. The naive endpoint name (from the WAHA docs section headers)
fails silently.

**Reality:** WAHA Core exposes the PTT (push-to-talk) voice endpoint as
`POST /api/sendVoice`. The payload is structurally identical to `sendImage`
(base64 file under `file.data` with `mimetype: "audio/mpeg"` and a
`filename`). The response body uses `audioMessage` (not `pttMessage`), and
the JSON includes `ptt: true` plus a `waveform` array — those are set by
WAHA, not by the caller.

**Working payload (Aug 2026, verified, example group → 30s MP3):**

```bash
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{
    "session": "default",
    "chatId": "120363000000000000@g.us",
    "file": {
      "mimetype": "audio/mpeg",
      "filename": "respuesta_example.mp3",
      "data": "<base64 of mp3>"
    }
  }' \
  http://127.0.0.1:3000/api/sendVoice
# Response: 201 Created with audioMessage containing ptt:true, seconds:29, waveform, mediaKey
```

**Discovery trick — when an endpoint name is uncertain, probe 4xx quickly:**

```bash
for ep in sendVoice sendAudio sendFile sendMessage; do
  curl -s -o /dev/null -w "%{http_code} $ep\n" \
    -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
    -d '{}' "http://127.0.0.1:3000/api/$ep"
done
# 400 = endpoint exists, payload missing/empty
# 404 = endpoint does NOT exist
# This catches 4 variants in <500ms before reading docs.
```

**Size budget (verified):** A 1MB base64 audio body (~30s MP3 at 256kbps)
runs fine in WAHA Core 2026.7.2. Larger payloads (>5MB) may need to be
uploaded to a public URL first and passed via `file.url` instead of
`file.data`.

**Pairing tip:** Synthesize the audio first (Kokoro local or MiniMax cloud),
copy to `~/Downloads/<name>.mp3` (the bridge whitelists this path, see
`janitor-voice` pitfall), then base64-encode for the WAHA payload. Don't
point WAHA's `file.url` at `file://$HOME/Downloads/foo.mp3` — it 404s
on local file URLs; pass base64 instead.

## Reading Group Message History

The endpoint for reading past messages of a chat (group or 1:1):

```bash
curl -H "X-Api-Key: $WAHA_API_KEY" \
  "http://127.0.0.1:3000/api/default/chats/{CHAT_ID}/messages?limit=100"
```

- `CHAT_ID` is the JID: `120363000000000001@g.us` for groups, `573001234567@c.us` for 1:1
- Query params: `limit` (default 25, max ~1000 in practice), `downloadMedia` (boolean)
- Response is an array of message objects: `{id, timestamp, fromMe, body, hasMedia, media, ...}`

**Returns 400** with `Enable NOWEB store config.noweb.store.enabled=True` if store
is off.

### Aug 2026 reality (NOWEB engine)

See **Pitfall #9 above** — NOWEB does NOT download backlog. In practice this
endpoint returned only a handful of messages for a busy VIP group: 1 sent by me
(the "🤖 (sincronizando)" ping), a few image-only messages from one contact, 1
text message from another. The remaining backlog from the same members was not
retrievable.

### Aug 2026 reality (engine fallback order for history)

| Engine | History access | RAM | Engine lib |
|--------|---------------|-----|------------|
| WAHA Plus (paid) | Full | depends on tier | All engines |
| WEBJS | Full but heavy | 600-800MB | Puppeteer + Chromium |
| WPP | Full but heavy | similar | Patch of WEBJS |
| NOWEB | None on reconnection, partial on fresh pair | 355MB | Node.js + protobuf |
| GOWS | Has the protocol bug (Pitfall #2), don't recommend | ~440MB | Go |

### When you actually need history

Build real-time webhook ingestion instead:

```bash
# Configure webhook to receive each incoming message live
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{"webhook":{
    "url":"http://127.0.0.1:5678/webhook/waha",
    "events":["message"]
  }}' \
  http://127.0.0.1:3000/api/sessions/default
```

Then any new message in any group fires a POST to your endpoint with the full
message body. Persist to NocoDB / file / etc., and you have your own history.

### Sending messages (the README on `/api/sendText`)

Standard call, returns `{id, _data, status}`:

```bash
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{"session":"default","chatId":"573001234567@c.us","text":"Hola"}' \
  http://127.0.0.1:3000/api/sendText
```

⚠️ **No delete endpoint** — see Pitfall #10. Messages sent are permanent.

## Extracting Group Participants

WAHA's `/api/default/groups` returns participant lists. Useful for catalogs, audits,
contact-list generation. **Two-tier data access** with very different capabilities.

### Tier 1 — Always available (from `/api/default/groups`)

⚠️ **CORRECT endpoint — Aug 2026 confirmed:** `GET /api/default/groups` (session name in path, **not** `/api/sessions/default/groups` and **not** `/api/groups`). Verified: the other two return 404 ("Cannot GET /api/sessions/default/groups", "Cannot GET /api/groups").

```bash
curl -H "X-Api-Key: $WAHA_API_KEY" http://127.0.0.1:3000/api/default/groups | python3 -m json.tool
```

**Response shape — NOT a list, it's a dict `{subject: metadata}`:**

```python
{
  "EXAMPLE PRIVATE GROUP": {           # ← subject IS the KEY, not a field
    "id": "120363000000000000@g.us",
    "subject": "EXAMPLE PRIVATE GROUP",  # ← echoed, but always check the key first
    "addressingMode": "lid",
    "owner": "734590423137@lid",
    "ownerUsername": "example_handle",
    "size": 10,
    "creation": 1646877969,
    "participants": [...],
    "isCommunity": false,
    "restrict": false,
    ...
  },
  "Other group subject": {...}
}
```

**Search pattern — must check both keys AND values:**

```python
# Exact match (case-insensitive, trimmed)
matches = [
    (k, v) for k, v in data.items()
    if k.strip().upper() == 'EXAMPLE PRIVATE GROUP' or v.get('subject', '').strip().upper() == 'EXAMPLE PRIVATE GROUP'
]

# Substring search
import re
matches = [(k, v) for k, v in data.items()
           if re.search(r'example\s+private', k, re.IGNORECASE)]
```

**Pitfall — regex word boundaries on multi-word group names:** regex like `r'private\b'` will NOT match `"EXAMPLE PRIVATE GROUP"` because `\b` requires a word boundary that doesn't exist between the space and the next word. Use `r'private'` (no `\b`) or `r'\bprivate\b'` only when the search term is the **last word** of the subject. For multi-word subjects, search for the last word without `\b` or use a substring match.

**Per-group fields available:**
- `id` (JID with `@g.us`)
- `subject` (also embedded as dict key)
- `addressingMode` (`lid` or `pn`)
- `owner`, `ownerPn`, `ownerUsername`
- `size` (authoritative member count)
- `creation`, `subjectTime`, `descTime` (unix timestamps)
- `desc` (group description, may be empty)
- `restrict` (only admins can edit info), `announce` (only admins can send)
- `joinApprovalMode`, `memberAddMode`
- `isCommunity`, `isCommunityAnnounce`
- `participants` (see below)

**Per-participant fields available:**
- `id` (LID, always present)
- `phoneNumber` (~81% of participants — business accounts hide this)
- `username` (~19% — handle like `@example_handle`)
- `admin` (`superadmin`, `admin`, or `null`)

For a large group: ~80% of participants expose a phoneNumber + ~19% expose a
username = ~100% coverage of at least one public field per person. Sufficient
for catalogs and bulk-message audiences. See `references/contacts-and-groups.md`
for the dump script, NOWEB store enablement sequence, snake_case gotcha, and
full endpoint reference.

### Tier 2 — Rich metadata (requires NOWEB store)

For `pushName`, `businessName`, `verifiedName`, `profilePicUrl`, you need:
```json
{"engine": "NOWEB", "noweb": {"store": {"enabled": true, "fullSync": true}}}
```

Then `GET /api/{session}/contacts/all` returns the full contact list with metadata.

### ⚠️ NOWEB fullSync bug (Aug 2026, confirmed)

**Symptom:** `noweb.store.fullSync=true` configured + 5+ minutes waiting +
`GET /api/default/contacts/all` returns **200 with empty body (0 bytes)**.
Logs show repeated:

```
WARN (NowebPersistentStore): got update for non-existent contact.
update: '{"id":"147768886689924@lid","notify":"Example Contact"}'
```

**Cause:** NOWEB persistent store attempts to update contacts that don't exist
in its own DB. The sync loop processes updates faster than inserts, so contacts
never land in the store. Result: empty contact list despite correct config.

**Workarounds (ranked by reliability):**

1. **Use Tier 1 only.** Accept the 81%/19% phone/username coverage. For most
   audit/bulk-message use cases, phoneNumber is enough.
2. **Switch to WEBJS engine** for the contact-extraction session. WEBJS has a
   functional store but is heavier (~600-800MB RAM, more detectable fingerprint).
3. **Wait for WAHA fix.** Issue tracked upstream; not yet released as of Aug 2026.

**Don't:** Do NOT spend more than 5 minutes waiting for sync to "complete" — it
won't. The 0-byte response is definitive, not transient.

### Searching by Name — Anti-Overdelivery Rules (Aug 2026)

When the user asks "look for group X" or "find the chat with Y", default to
**search-and-show-one**, NOT to "download all groups and parse them". The
user wants the answer to their question, not a catalog.

### The rule

```python
# 1. ONE call to /api/default/groups (the dict endpoint)
# 2. Filter to the single match (or empty list)
# 3. Return ONLY the match, with the fields the user actually needs
# 4. Do NOT dump the full group catalog.

WAHA_API_KEY = ...
groups = json.loads(curl GET /api/default/groups)  # dict keyed by subject

target = "EXAMPLE PRIVATE GROUP"
match = next(
    ((k, v) for k, v in groups.items()
     if k.strip().upper() == target.upper()
     or v.get('subject', '').strip().upper() == target.upper()),
    None,
)
if not match:
    return "No match for 'EXAMPLE PRIVATE GROUP' across N groups."
return format_match(match)  # ONE group, with the fields asked
```

### What over-delivery looks like (and why to avoid it)

When the user asks "busca el grupo EXAMPLE PRIVATE GROUP", the WRONG response is:

```
Fetched N groups. Indexes: 0..N-1. Total: N. Type: dict. Sample[0]: ...
M groups where you are member. Searching for 'example' or 'private' → 0 hits.
Searching regex for 'example|...|...' → 0 hits.
Searching with: r'example\b', r'private\b' → 1 hit.
```

This is **what an over-eager agent does** — and the user implicitly rebukes it
by responding with a curt one-liner ("Busca el grupo EXAMPLE PRIVATE GROUP").
The user did NOT ask for a catalog. They asked for ONE group.

### What the right response looks like

```
Found: EXAMPLE PRIVATE GROUP
  JID: 120363000000000000@g.us
  Members: 10 (recovered from size field)
  Owner: @example_handle (superadmin)
  Created: 2022-03-10
  You: miembro
```

### When to dump the full catalog

- The user explicitly asks for "list all groups" / "auditoría de todos mis grupos"
- The user is debugging "why can't I find X" and explicitly asks "show me what you have"
- The user says "diff contra X" and you need participant lists from multiple groups

For all other cases, search-filter-return-one.

### Reusing the search code

A reusable search helper is in `scripts/search-waha-chat.py` (Aug 2026).
Accepts: name substring, regex, JNID, exact subject match. Returns at most
N matches with the relevant fields. Use it before falling back to manual
list comprehension.

## Updating session config (PUT, not POST)

WAHA's docs show `POST /api/sessions/{name}` for updates — this returns **404**.
The correct method is **`PUT`** (per `@Put(':session')` decorator in the source).
Other session endpoints (`start`, `stop`, `restart`, `logout`) are POST.

```bash
# Update config (engine + store settings)
curl -X PUT -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{"config":{"engine":"NOWEB","noweb":{"store":{"enabled":true,"fullSync":true}}}}' \
  http://127.0.0.1:3000/api/sessions/default
```

**Auth preservation caveat:** PUT applies to config immediately, BUT if the session
is already `WORKING`, the engine does **not** restart to pick up new config — logs
show `"Reconnection with existing sync data, skipping history sync wait"` (this is
the literal log line — search for that exact phrase when debugging). You must
`stop` first, then `PUT`, then `start`. Auth state is preserved across this sequence
(no re-pairing needed) as long as the engine is the same.

**Exception — store config requires full re-pair:** Flipping `noweb.store.enabled`
or `noweb.store.fullSync` is NOT a clean config swap. The persistent store binds
to the session identity at first start; subsequent restarts don't pick up the
toggle, and the engine keeps using the old store state in memory. The working
sequence is:

```bash
# 1. Stop, logout (this unlinks the device on WhatsApp's side), delete session
curl -X POST .../api/sessions/default/stop
curl -X POST .../api/sessions/default/logout
curl -X DELETE .../api/sessions/default

# 2. Recreate with store config set from the start
curl -X POST .../api/sessions \
  -d '{"name":"default","config":{"engine":"NOWEB","noweb":{"store":{"enabled":true,"fullSync":true}}}}'

# 3. Start, request pairing code, user scans/inputs — full re-pair required
```

This burns the previous auth token; the user must re-pair their phone (scan QR
or input pairing code). Don't promise "config change without re-pair" when the
config touches the store.

### camelCase vs snake_case in WAHA config

WAHA's API accepts `fullSync` (camelCase), NOT `full_sync` (snake_case). Other
config keys follow the same pattern (`markOnline`, not `mark_online`).
The session response echoes whatever case WAHA normalized to (always camelCase).

## Troubleshooting

### Container restart loop / health: starting forever

```bash
docker logs janitor-waha --tail 50
```

Common causes:
- **401 on /health** → you rotated `WAHA_API_KEY` in `waha.env` but the container
  still has the old one. Force recreate:
  ```bash
  cd ~/.janitor/docker && docker compose --env-file waha.env -f waha-compose.yml up -d --force-recreate
  ```
- **EACCES on /app/.sessions** → bind mount dir created as root. Fix ownership
  (verify inside container first: `docker exec janitor-waha id`):
  ```bash
  CONTAINER_UID=$(docker exec janitor-waha id -u)  # usually 1000 (node)
  sudo chown -R $CONTAINER_UID:$CONTAINER_UID ~/.janitor/docker/waha/sessions ~/.janitor/docker/waha/media
  ```

### Pairing code rejected as "incorrect" (GOWS bug, see Pitfall #2)

Fix is to switch to NOWEB:
```bash
WAHA_API_KEY=$(grep '^WAHA_API_KEY=' ~/.janitor/docker/waha.env | cut -d= -f2)

# Stop + delete current session
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" http://127.0.0.1:3000/api/sessions/default/stop
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" http://127.0.0.1:3000/api/sessions/default/logout
curl -X DELETE -H "X-Api-Key: $WAHA_API_KEY" http://127.0.0.1:3000/api/sessions/default

# Recreate with NOWEB
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{"name":"default","config":{"engine":"NOWEB"}}' \
  http://127.0.0.1:3000/api/sessions
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" \
  http://127.0.0.1:3000/api/sessions/default/start

# Make NOWEB default for future sessions
sed -i 's/^WHATSAPP_DEFAULT_ENGINE=.*/WHATSAPP_DEFAULT_ENGINE=NOWEB/' ~/.janitor/docker/waha.env
```

### Endpoint error codes when session is missing (for tooling reference)

| Endpoint | Missing session response |
|----------|--------------------------|
| `GET /api/{session}/auth/qr` | **422** with `"Session \"<name>\" does not exist"` |
| `GET /api/sessions/{name}/me` | **404** with `"We didn't find a session with name '<name>'"` |
| `GET /api/{name}/me` (WAHA docs typo) | **404** with `"Cannot GET /api/<name>/me"` |
| `POST /api/{session}/auth/request-code` | **404** with `"We didn't find a session with name '<name>'"` |

Use these to distinguish "session doesn't exist" (need to `POST /api/sessions`)
from "session exists but not started" (need `POST /api/sessions/{name}/start`).

### QR code / pairing code expires before use

Both expire in ~60s. Re-request without restarting the session:
```bash
# QR
curl -H "X-Api-Key: $WAHA_API_KEY" http://127.0.0.1:3000/api/default/auth/qr -o /tmp/qr.png

# Pairing code
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" -H "Content-Type: application/json" \
  -d '{"phoneNumber":"573001234567"}' \
  http://127.0.0.1:3000/api/default/auth/request-code
```

### `SCAN_QR_CODE` hangs after scan

The phone scanned but the session didn't transition to `WORKING`. Wait 30-60s —
the handshake takes a minute sometimes. If still stuck:
```bash
# Restart the session
curl -X POST -H "X-Api-Key: $WAHA_API_KEY" \
  http://127.0.0.1:3000/api/sessions/default/restart
```

### `PASSKEY_REQUIRED` / `PASSKEY_CONFIRMATION_REQUIRED` status

Some accounts get an extra WebAuthn prompt from WhatsApp after pairing. GOWS-only feature.
If this hits with NOWEB:
- The event payload `data.code` contains the challenge to confirm
- For `PASSKEY_CONFIRMATION_REQUIRED`: tell the user "type this code in WhatsApp"
- For `PASSKEY_REQUIRED`: WAHA signs the challenge automatically — just wait

### `WAHA_NAMESPACE=all` matters for multi-session

If you create a second session with the same `name` (e.g. two "default"), they
collide. Use unique names: `default`, `secondary`, etc. The env var
`WAHA_NAMESPACE=all` allows multiple namespaces per worker.

## Group Member Diff Against an External Base (CRM, NocoDB, etc.)

Reusable pattern for "who's new in the group, who's left, who's already known".
Proven Aug 2026 against `120363000000000001@g.us` (example large group, sizes
225→259→272→257→259 across 4 runs). See `scripts/diff-waha-group.py` for the
working implementation.

### The methodology (5 steps)

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 1. Preflight   - Verify WAHA session WORKING                            │
│                  Verify external base auth fresh                         │
│ 2. Source      - GET /api/default/groups → group metadata + participants│
│                  (alternative: GET /api/{session}/groups for specific)    │
│ 3. Base        - Page through external base, extract unique LIDs + any   │
│                  second key (phone, username, etc.)                       │
│ 4. Diff        - Compare on whichever key matches the user's intent:     │
│                  • by LID     → strict (member identity)                  │
│                  • by phone   → strict on phone-visible subset           │
│                  • by username → strict on business-accounts subset      │
│ 5. Classify    - buckets: NEW (in group, not in base)                     │
│                         KNOWN (in both)                                    │
│                         EXITED (in base, not in group)                     │
└──────────────────────────────────────────────────────────────────────────┘
```

### Three diff flavors — pick one

| User asked for | Diff key | Caveat |
|----------------|----------|--------|
| "Contactos que ya no están en la base" | `base - group` (excluding for the BASE side, but you want to know who's NOT in the group anymore — see notes) | This is `EXITS`, requires re-presenting in reverse; in practice base ∩ group is the truth and base - group is "salió del grupo o fue removido" |
| "Hay nuevos números?" | `phone ∉ base.phone` | Misses ~19% of members (business accounts hide phone) |
| "Qué contactos no tenemos del grupo" | `group.lid ∉ base.lid` | Catches everyone with an LID |

**Default to LID-based diff** unless the user is specifically asking about a
narrower signal (phone count, username presence). LID is the primary key WAHA
gives you. Phone/username are derivative secondary keys.

### Inserting the new ones safely (3 preflight guards)

Before any `INSERT` of new contacts:

1. **Dedupe against base** — query `base.lid` and `base.phone` for each would-be
   insert. If either matches an existing record, skip (don't update; don't
   duplicate). Aug 2026 the test group had a duplicate that was already inserted
   by a previous run; this guard caught it.
2. **Set `source_group` and `source_group_id`** explicitly in every new record
   so future diffs are scoped to the group of origin.
3. **Bulk insert in one POST** with an array of records. WAHA's auth flow was
   tested with a 225-record bulk insert (single batch, ~700ms). Don't loop.

### Phones are regional — normalize before diff

Phone numbers across countries look different. Normalize before dedupe:

```python
def normalize_phone(p):
    if not p: return None
    s = str(p).replace("@s.whatsapp.net", "").replace("+", "").replace(" ", "").replace("-", "")
    return s if s.isdigit() else None
```

Aug 2026 test group: 80% `+57` (Colombia), 1% `+1` (US), 1% `+34` (ES),
~18% no phone. Without normalization, "+57 300 1234567" and "573001234567@c.us"
look like different strings.

### Aug 2026 drift numbers (example group)

A real example of why this skill exists:

| Run | WAHA size | Base size | New | Exited | Net Δ |
|-----|-----------|-----------|-----|--------|-------|
| Initial load | 225 | 0 | 225 | 0 | 225 |
| After 1st add | 257 | 225 | 32 | 0 | +32 |
| After 2nd add | 258 | 257 | 2 | 1 | +1 |
| After 3rd add | 255 | 259 | 0 | 4 | -1 |
| After 4th add | 255 | 260 | 1 | 0 | +1 |

When WAHA size < base size, do **not** delete from the base — the user may
have other reasons to keep the records. Always report the exited bucket as
**candidates** and let the user decide what to do. (See the user's first-class
constraint: "No borres a nadie de la base, dame los datos de los que se salieron
del grupo.")

### Implementing in NocoDB or similar

The NocoDB workflow that proved cleanest (Aug 2026):

```bash
# Step 1: Create a base + table with a unique column on 'lid' (NocoDB: SingleLineText with unique=true)
# Step 2: Bulk insert with array POST, ~700ms for 225 records
# Step 3: Add labels (MultiSelect column) in bulk via PATCH /records
# Step 4: Future diff runs call this same script, report deltas, propose inserts
```

See skill `janitor-nocodb` for the API surface; this skill's
`scripts/diff-waha-group.py` calls both WAHA and NocoDB and produces
markdown-formatted reports.
